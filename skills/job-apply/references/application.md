# Filling and durable handoff

Read [browser.md](browser.md) before any browser work and [intake.md](intake.md) before acquiring an ordinary job. Retain the same canonical job and managed resume throughout.

### Phase 2: Application Filling

1. **Initialize and load storage** through the bundled `answer-memory` skill. Read `application-run-status`, require the exact job in its current queue, then read only that run's selected resume with `resume-facts-get --resume-id <confirmed-resume-id>`. Verify its confirmed fact and content revisions still match the application run selection, then inspect `node "<plugin-root>/apps/companion/command.mjs" task [--root <resolved-root>] activity --id <job-id>` for resumable work on the exact selected canonical job. Use that fact set for applicant profile fields. For every ordinary application, use the acquired canonical job ID as the application/session ID and the managed resume returned by the private helper. If no suitable managed resume exists, ask the user for a source file, import it with `resume-import`, then return to extraction, owner fact review, and application run setup. Never use `profile.resumePath`, a URL-derived session ID, or a user source path for upload. The authenticated loopback QA replay remains the only synthetic coordinator exception.

If the run's selected resume content or confirmed fact revision changes after acquisition, stop browser work. Use a value-free `needs_info` handoff to release the claim, complete the stale run, then ask for fresh chat confirmation before starting a replacement run. Never continue filling from a stale version.
2. **Continue in the host-managed visible browser** from the early account check, or open the canonical URL if no tab exists. Identify the job site and application flow without discarding an existing signed-in draft
3. **Pause for user-only steps** if login, password, CAPTCHA, MFA, or account creation appears. Route consent and acknowledgment controls through [reusable consent intents](consent-intents.md); pause for live-form approval before acting on them
4. **Open the application form**; if the early check already followed an external Apply link, continue in that visible tab. Otherwise, if a clearly non-final Apply link opens an external portal, continue in the same host-managed browser session
5. **Read the form**, apply the current mode in [application automation](application-automation.md), obtain Guided consent or an authorized higher-mode action decision, then fill profile-backed fields. For recurring questions call `node "<plugin-root>/apps/companion/command.mjs" task [--root <resolved-root>] semantic-lookup --input <private-json>` with the ephemeral visible question, exact scope, closed field class/sensitivity, policy mode, and explicit current-use authority. The Store recomputes candidates against current canonical answers and returns only opaque keys, confidence bands, and reason codes. Never reuse an uncertain, scope-drifted, incompatible, pending/deleted, unseen, or sensitive answer without current `per_use` authority (or an exact sensitive-answer binding in the active application grant). Use `approval-preview` followed by `approval-approve --owner-confirmed` for multiple fields; preserve current use, remember, policy mode, and use authority independently per field. If no record matches, ingest the value-free question (or an inferred candidate) with `answer-observe`; never create a separate question inbox or copy its answer into session/history metadata.
6. **Apply matching saved answers during the approved filling pass**. Once the owner has approved filling this exact visible application, enter accepted, confirmed, non-sensitive answers whose question, scope, and field class match. Do not ask the owner to restate a known value or approve each ordinary answer. Show and confirm `inferred` answers and ask only for `missing` answers. An unsupported or uncertain semantic match is not a known answer.
7. **Check current-use authority for sensitive saved answers before asking again**. For salary, work authorization, visa status, demographic information, disability disclosure, and similar fields, inspect the exact current-form approval or active application grant. If it already names the specific saved answer and destination for this form, use it once and do not repeat the prompt. Otherwise bundle the newly observed sensitive fields into one field-specific current-use request; the owner never needs to enter an already saved value again. Keep permission to fill separate from permission to remember, and use `--remember-sensitive` only after explicit field-specific retention consent. A consent or acknowledgment answer records a purpose-specific decision, not authority to act: match the live purpose, obtain any required action-time approval, and express the decision through the observed control as described in [reusable consent intents](consent-intents.md).
8. **Upload the resume** using the exact private `path` returned by `store resume-resolve --id <confirmed-resume-id>` for this run. Immediately before opening the chooser, run `node "<plugin-root>/apps/companion/resume-upload-guard.mjs" --id <confirmed-resume-id> --expected-revision <selected-resume-revision> --candidate-path <proposed-chooser-path>` (pass the same `--root` when the Store uses an override). This code guard resolves the Store again and rejects a path that differs from the current managed copy, a stale revision, or an unavailable file. Pass the successful guard's returned `path` unchanged to the selected visible browser's file chooser. Never construct an upload path from a Store root, resume ID, or `managedFile` basename; `resume-check` confirms the record but does not supply the browser path. Verify the ATS's accepted filename or accepted-file state. Follow the failed-upload recovery in [browser.md](browser.md) if either guard or upload fails.
9. **Save resumable progress** by putting only the value-free session object in a private temporary JSON file, running `node "<plugin-root>/apps/companion/command.mjs" attempt [--root <resolved-root>] progress --input <private-temp.json>`, requiring `progress_saved`, and immediately removing the input. Bind it to the post-acquisition `attemptRevision`; question text is ephemeral and the Store strips it before persistence. Durable pending fields, typed blockers, approvals, and browser handoff contain only closed metadata and opaque references—never values, identities, URLs, paths, filenames, digests, tab IDs, or browser state. Do not add an owner, Store, claim, command, token, or final-action authority field. This is a new stateless client; it does not need the launcher process or any earlier tool session. The authenticated loopback QA replay uses only its documented coordinator commands.
10. **Handle inaccessible controls** using the fallback rules in [browser.md](browser.md), or leave the field for the user
11. **Advance through non-final steps** only when the control is clearly Next,
    Continue, Save, or Review. When
    `profile.applicationPreferences.progressionMode` is `guided`, pause for the owner
    before every page transition. An explicit pacing request for the current
    application overrides the saved preference without rewriting it.
12. **Stop at final review** before any Submit, Send, or equivalent final-action button
13. Read [current-form readiness](readiness.md) for the live inventory and packet contract. **Complete the durable handoff** only after observing the current form and constructing a closed readiness packet for the current attempt. Enumerate all visible editable controls, including company-specific required and optional questions, and attest that the inventory is complete. Put `attemptRevision` plus `readinessInput` containing the exact revision, `evidenceKind: agent_attested_current_attempt`, the value-free `observedForm`, its recomputable `formManifest`, the current observation, and the expected observation revision in the private review-session file. This is your explicit attestation about the visible form, not independent proof of browser provenance. If a control cannot be enumerated or verified, use a typed Needs Attention handoff. Run a fresh `node "<plugin-root>/apps/companion/command.mjs" attempt [--root <resolved-root>] handoff --status awaiting_review --input <private-temp.json>`, require one `handed_off` response, and immediately remove the input. The Store recomputes the closed report and rejects replay-only, stale, inaccessible, incomplete, mismatched-control-manifest, validation-error, rejected-upload, unavailable-final-control, final-action-activated, pending-field, blocker, or alternate-handoff evidence without releasing the claim. On success it atomically saves only the value-free report and closed owner-review handoff, records `reviewed`, moves the job to `awaiting_review`, releases the claim, and exits. Never fall back to raw `claim-handoff`. A rejection means stop and re-evaluate; never reload and retry against unseen state. Replay success is not live upload proof. Tell the owner to inspect the visible page and submit manually.

If selected-ready work needs one non-sensitive user answer, put this exact session object in a private temporary JSON file (substituting the exact current attempt revision, visible question, and canonical answer key):

```json
{"status":"active","step":"questions","attemptRevision":17,"answerKeys":[],"pendingFields":[{"question":"How did you hear about this opportunity?","state":"missing","answerKey":"source.discovery","sensitive":false,"fieldClass":"source"}]}
```

Add the exact post-acquisition `attemptRevision`. A pending item may also carry a closed `fieldClass`, matcher confidence, and matcher reason codes. The question is ephemeral adapter input and is stripped before the Store commits the session; durable blockers are typed and reference-only. Run `node "<plugin-root>/apps/companion/command.mjs" attempt [--root <resolved-root>] handoff --status needs_info --input <private-temp.json>`, require `handed_off`, and immediately remove the input. Never include an answer/profile value, employer/role identity, path, URL, filename, digest, token, tab ID, browser state, or final-action authority. A missing profile-backed fact is not an answer-backed pending field: have the owner correct and reconfirm the selected resume facts separately.

Do not reload the job revision before this handoff; a conflict must expose concurrent changes. The broker atomically moves the job to `needs_info`, records `job-blocked`, releases the claim, emits one `handed_off` response, and exits. For an accepted, confirmed non-sensitive answer, use the exact-revision [task resolution route](recovery.md); if it becomes Ready, start a fresh detached broker for that same exact job. A sensitive pending answer instead follows recovery's live-form new-attempt route and requires fresh current-use approval before the control is changed. Never retain a broker or claim while waiting for the user. If the broker is lost, leave the record intact for explicit stale recovery; never delete or silently clear a claim.

User confirmation never authorizes this skill to click Submit, Send, or any equivalent final-action button.

### Durable to-do checklist for a Needs Attention handoff

Before `attempt handoff --status needs_info`, finish and verify every approved field the browser supports. Include `handoffChecklist` in the same value-free session input, with one code per remaining owner action. Repeat a code for separate controls needing the same kind of action; the list supports up to 32 actions. Use only these closed codes: `resume_upload`, `passport_country`, `country_of_residence`, `age_over_18`, `profile_fact`, `saved_answer`, `required_question`, `consent_choice`, `sign_in`, `verification`, `captcha`, `browser_control`, and `other_required_field`. Choose the most specific code supported by the observed form; use a general code only when none fits. Do not include question text, an answer, a filename, or a browser identifier. This checklist describes outstanding work and grants no authority to fill or submit. If a required upload fails while three unanswered fields remain, for example, record `["resume_upload","passport_country","country_of_residence","age_over_18"]`. The Companion shows the closed checklist alongside blockers. Older attempts without one retain their existing generic blocker display.

The checklist persists across progress writes and attempts when the field is omitted. Explicitly replace it with the remaining actions as each is resolved, then send `handoffChecklist: []` after all are complete. An `awaiting_review` handoff cannot retain outstanding checklist actions; the owner still performs final submission manually.
