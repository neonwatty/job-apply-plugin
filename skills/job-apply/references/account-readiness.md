# Early account check

Run this after the owner has chosen an exact canonical job and placed it in the active application run, before `task select` or browser filling. It is read-only and does not configure an account or grant sign-in authority.

1. Read the selected job's exact URL with `store job-get --id <job-id>`. Classify that URL with `store account-flow-classify --url "$portal_url"`. Use the classifier's `status`, `adapterId`, `flowKind`, `accountRequired`, and opaque `realmRef`; do not guess requirements from the hostname, job-board label, or an ATS name in a query string. Keep URL and applicant values out of durable progress and user-facing receipts.
2. For a classified account-required flow, read `store employer-account-get --realm-ref <realm-ref>` for public, redacted metadata. Report whether a record exists and its lifecycle, without treating a record, Keychain metadata, or an `active` lifecycle as proof of a current browser session. A missing or discovered record means account setup may be needed, not that the user definitely lacks an account. Do not create a record merely to clear this check.
3. In Guided mode, inspect the exact job's existing visible tab or open its canonical URL **before `task select` and attempt acquisition**. Follow [browser](browser.md) for the visible host-managed browser. If a clearly non-final application link leads to an external portal, follow that navigation, classify the observed destination URL, and repeat the redacted metadata check for any account-required flow. Never activate an ambiguous or final-action Apply control. This is a read-only authentication preflight; do not enter applicant information. If the current page requires sign-in, account creation, email verification, CAPTCHA, or MFA, tell the owner the observed step and leave the job queued with no claim. The owner completes it manually, then the agent rechecks the visible page and resumes the ordinary selection and attempt sequence. Do not request or handle passwords, codes, or browser secrets.
4. A classified accountless flow can continue normally. An unresolved classification is unknown, not accountless: inspect the visible page before filling and use the same owner handoff if an authentication gate appears. If the browser is already signed in, continue; no account prompt is needed.
5. For an already acquired job or a bounded higher-mode campaign, preserve its claim and follow the typed authentication interrupt and `needs_info` handoff in [application automation](application-automation.md) and [filling and handoff](application.md). Do not leave a claim held while waiting for the owner or repeatedly select the same blocked campaign job.

This check is about **account readiness**. Per-realm email configuration, any protected credential metadata, and the live browser session are separate states. Direct Greenhouse job applications can be accountless; Workday tenants can require separate accounts; MyGreenhouse uses an email code. Never offer a universal ATS login or shared password as an inferred convenience.
