# Canonical application intake

Read before starting an ordinary application. For an existing reviewed or blocked job, read [recovery.md](recovery.md).

First determine the application mode:

- The authenticated loopback QA replay in [QA routing](../../answer-memory/references/qa-replay.md) is the only exception to canonical URL intake. Keep using its resolved run ID and coordinator lifecycle; do not create a canonical job for that synthetic fixture.
- If the user supplied a job URL, the required ordinary behavior is canonical intake: put only the supported canonical job fields in a private temporary JSON object, run `node "<plugin-root>/apps/companion/command.mjs" task [--root <resolved-root>] intake --input <private-temp.json>`, and immediately remove the input. Do this before any browser work. A conflict, invalid identity, unavailable store, or any other non-success result stops the workflow without opening a browser. Retain only the returned canonical job ID, status, and revision; the task result never returns the URL or an upsert token.
- For ordinary discussion or when no URL was supplied, run `node "<plugin-root>/apps/companion/command.mjs" task [--root <resolved-root>] snapshot`. List and compare only its canonical jobs and Needs Attention projection. Do not run the legacy `job-list --status ready` command as the ordinary agent discussion surface. Never infer a choice from priority, ordering, a URL mention, or model preference: ask the owner to choose one exact canonical job unless their current request already explicitly names that exact job as the application target.
- Before `task select`, run `store application-run-status`. If no run is active, list available managed resumes and their value-free `resume-facts-list` summaries. When the current message explicitly requests Job Apply for one exact job through manual review, exactly one active resume is the default, and that resume has current confirmed facts, treat that request as authorization to bind the exact current resume and fact revisions to this run. Report the selection in a non-blocking progress update and do not ask for a redundant run confirmation. Otherwise, present the proposed queue, candidate resume labels, and each resume's fact state, then ask the owner to choose one resume and confirmed fact revision. If the chosen resume has no current confirmed facts, pause for extraction and owner review; do not substitute applicant-wide profile facts or another resume's facts. Put the exact initial job IDs in a private `{"jobIds":[...]}` file and run `store application-run-start --resume-id <resume-id> --expected-resume-revision <resume-revision> --expected-fact-revision <fact-revision> --owner-confirmed --input <private-file>`, then remove the file. This run authorization never grants post-readiness fill consent or final-action authority.
- If a run is active, use its selected resume and fact revision without asking again. The target job must appear in its latest queue version. To add or remove jobs, show the proposed full queue in chat, write its exact IDs to a private `{"jobIds":[...]}` file, and run `store application-run-update --run-id <run-id> --expected-revision <run-revision> --input <private-file>`. Remove the file immediately. Queue updates append a revision and never change the run's resume or facts. An actively claimed job cannot be removed. Use `application-run-complete --run-id <run-id> --expected-revision <run-revision>` before choosing another resume or fact revision.
- A changed resume file or newer draft/confirmed fact revision makes the active run selection stale and stops application work. Complete that run and obtain fresh chat confirmation before starting a replacement run. Do not silently switch inputs within a run.
- After an explicit owner choice, run `node "<plugin-root>/apps/companion/command.mjs" task [--root <resolved-root>] select --id <job-id> --expected-revision <displayed-revision> --owner-confirmed`. This exact-revision operation re-runs readiness preflight, marks an eligible saved or needs-info job Ready, and returns a stable no-op when the exact job is already Ready. On success, discard the pre-select displayed revision and retain the exact revision returned in `select.job.revision`; pass that returned revision, unchanged, to the private attempt helper described below. Any stale revision, failed preflight, conflict, unavailable record, or other non-success result stops without browser work; do not run `job-acquire`, do not start an attempt, and refresh the task snapshot to discuss the changed state rather than retrying against unseen data.
- Before starting the selected Ready job, run `claim-status`. If it returns any live or expired claim, identify only the claimed job and stop: the ordinary agent route cannot recover, steal, clear, or replace it. An interrupted attempt remains for explicit expiry/recovery outside this skill. If there is no claim, start only the explicitly selected canonical job as described below.



For a selected Ready job, use only the exact revision returned by the successful `select` result, create a short non-sensitive owner label for this agent run, and run one short launcher client: `node "<plugin-root>/apps/companion/command.mjs" attempt [--root <resolved-root>] start --id <job-id> --owner <owner-label> --expected-revision <select.job.revision>`. Never use the pre-select displayed revision. For the separately authorized reviewed-job path, use only the `restart-review` launcher and exact revision in [recovery.md](recovery.md). Either client returns one redacted failure or `acquired` with the exact job URL/revision and managed resume identity/path needed for the application, then exits. Acquisition or restart starts one OS-detached broker scoped to the resolved Store. No launcher, stdin, PTY, tool session, or conversational process must remain alive. The broker privately acquires once, retains the bearer only in memory, automatically heartbeats at least every 60 seconds, and accepts later stateless clients only through its OS-user-restricted Store socket. It never accepts a different job, revision, owner, Store, or claim. Never invoke the Store's raw acquire, review-restart, recovery, heartbeat, progress, or handoff commands in an ordinary workflow: in particular, never run `job-acquire --id <job-id> --owner <owner-label> --expected-revision <select.job.revision>` or raw `job-review-restart`. Never put claim authority in argv, environment, input, output, files, runtime metadata, diagnostics, reports, or receipts.

To request an immediate heartbeat from any later conversational turn, run a fresh client: `node "<plugin-root>/apps/companion/command.mjs" attempt [--root <resolved-root>] heartbeat` and require one successful `heartbeat` response. The client exits immediately; the detached broker continues independently. A rejected command or unavailable broker stops browser work. Broker loss leaves the exact existing claim untouched for expiry and explicit recovery; a new launcher cannot adopt, replace, recover, or reset it.
