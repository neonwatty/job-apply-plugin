## Resume fact extraction

Use this workflow when the owner asks about resume facts or supplies an exact extraction request. Do not scan requests during every application.

For a follow-up that explicitly approves a draft already reviewed by the owner,
inspect the current summary with `resume-facts-list`. Match the named resume,
fact revision, and content revision to the reviewed draft before running
`resume-facts-confirm`. A changed revision requires another private review.
Stop after confirmation.

1. On first use, ask for the local resume path if none was supplied. With owner authorization, resolve the path locally and use the managed import in [resumes](../../answer-memory/references/resumes.md). For an already managed resume, use its current ID and revision. Create the scoped request for that exact resume if none exists, unless the owner opted out. Do not require a pre-existing request for a new resume.
   For an existing queued request without an ID, list requested items with `resume-extraction-request-list --status requested`. Let the owner choose if several are open. Read only the chosen request with `resume-extraction-request-get --id <id>`, retaining its revision and resume ID.
   For a copied Companion handoff, the opaque request ID is the only mutable value. Do not ask the owner to share, or echo back, resume data, candidate data, file paths, or filenames.
2. Resolve only that managed resume with `resume-resolve --id <resume-id>`. Read the complete file with a document-capable local tool. Privately build a permission-restricted temporary JSON object containing facts supported by that resume. Verify every scalar against the full document and keep complete structured work, education, and skill entries. Omit uncertain details. Never copy facts from another resume or the applicant-wide profile.
3. A request with `scope: "resume"` uses `resume-extraction-request-complete-scoped --id <id> --input <private-candidate.json> --expected-request-revision <revision>`. It creates a draft under that resume only. Tell the owner the draft is ready, using field names and the exact revision without applicant values. Offer private terminal review using `resume-facts-get --resume-id <id>` as described in [resumes](../../answer-memory/references/resumes.md). Companion’s **Resumes → [resume] → Facts** is optional. In a follow-up that explicitly approves the privately reviewed draft, run `resume-facts-confirm` with its exact fact and content revisions. Never infer approval from the request to extract, a generic “continue,” or a different revision.
4. An older request without `scope` retains the legacy proposal workflow. Read `profile-inspect` for its revision and `resume-proposal-list --resume-id <resume-id> --status pending --summary-only` for a possible superseded proposal. Complete with `resume-extraction-request-complete --id <id> --input <private-candidate.json> --expected-request-revision <request-revision> --expected-profile-revision <profile-revision>`, adding `--expected-pending-proposal-id <proposal-id>` only when exactly identified. Tell the owner that this is a legacy profile proposal, not a resume fact set.
5. If no credible candidate can be produced, call `resume-extraction-request-fail` once with its exact revision and one approved reason: `content_unreadable`, `unsupported_resume`, `extraction_failed`, `candidate_invalid`, or `interrupted`. On revision or content conflict, discard the candidate and stop; do not retry unseen data.
6. Delete the temporary candidate and all temporary resume data after success, failure, conflict, or interruption. Keep values, paths, filenames, and bytes out of chat, logs, receipts, and diagnostics. Stop at owner review or confirmation. Begin application browser work only from a separate authorized application request.

Companion import or replacement requests scoped extraction by default unless the owner opts out. After an agent imports or replaces a resume through the Store CLI, run `resume-extraction-request-create --resume-id <resume-id> --expected-resume-revision <saved-revision> --scope resume` unless the owner opted out. A queued request is visible even when no agent is present to process it.
