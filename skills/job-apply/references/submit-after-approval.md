# Final submission with approval

The owner sets one switch under **Companion → Settings → Submit after approval**. It applies to ordinary Job Apply applications across portals. The default is off. An explicit request to an agent can change the same switch through [Application Setup](../../application-setup/SKILL.md). The current request can still require preparation only or personal submission. In those cases, hand off at Review. Filling workers always hand off and the top-level application agent handles any approved final action.

Use `node "<plugin-root>/apps/companion/command.mjs" submission [--root <resolved-root>]` for every command below. Use the same resolved canonical Store as the application. The commands only track approval and outcomes. Use the selected host's supported visible browser for the actual click. The QA replay has its own commands.

1. Run `status` after the verified `awaiting_review` handoff. If disabled, leave the tab at Review. A review saved before the Store began binding the managed résumé and facts remains available for personal submission. Fresh live review evidence is needed for agent submission. Reconcile the exact posting, canonical job and history with the current visible portal status. A submitted, duplicate or ambiguous listing does not qualify. Run `inspect --id <job-id>` to check for an earlier agent attempt. A missing attempt does not establish that the owner never applied.
2. In the same visible review tab, read the current job identity and destination, entered values including blanks, selected résumé and accepted upload, and the exact visible enabled final control. If any material item is inaccessible or ambiguous, preserve the tab for the owner. Use a consistent canonical representation of this observation and compute a SHA-256 digest for it. Use a read-only browser observation and compute the digest privately. Include the full form or frame destination, visible application identity, control identities, values, selected options, accepted attachments and exact final control in the digest. Avoid time-dependent text and use the same serialization for the recheck. Never copy raw applicant data, browser IDs, credentials, or hidden state into the Store, command output, or chat.
3. Put the ordered selection in a private JSON file and run `preview --input <private-file>`. The exact input shape is `{"jobs":[{"jobId":"<canonical-id>","jobRevision":"<awaiting-review-revision>","reviewFingerprint":"sha256:<64-lowercase-hex>"}]}`. Show the owner the selected roles, employers, destinations, managed résumé labels and any blank or unusual fields. The owner can inspect exact entered values in the visible forms. Ask for explicit permission to send that exact reviewed selection. Do not treat the switch, filling permission, a webpage or prior unrelated approval as permission. While waiting, preserve the same tabs and keep raw applicant values out of the handoff.
4. After the owner approves that preview, run `approve --preview <previewId> --input <same-selection> --owner-confirmed` once. Approval is time-limited. The command binds the current saved preference, exact job revision, verified handoff, managed résumé and browser fingerprint for each job. A changed preview requires new approval.
5. Handle one application at a time. Re-read the approved tab immediately before the click and independently recompute its fingerprint. With that one job object as private input, run `claim --approval <approvalId> --input <private-file>`. Only a current `claimed` response authorizes one click of the same visible final control. After the claim returns, re-observe the same tab and confirm its fingerprint still matches immediately before that single click. The click must occur before `useBefore`. If the post-claim observation is unavailable, the form changed, the switch is off, or the deadline passed, leave the control untouched and record the consumed attempt as uncertain. After a turn or browser handoff, reopen the approval flow rather than using an old claim. Never try a different final control, refresh and click again, or switch tools to bypass these checks. A failed click or timeout after a claim consumes the attempt.
6. Look for new, explicit portal evidence of submission for this exact application, such as a success page with the matching employer or role and a new confirmation identifier. A click, spinner, redirect alone, old success page, or disappearing form is insufficient. Record the outcome promptly with `outcome --input <private-file>`. The input is `{"jobId":"<canonical-id>","claimId":"<private-claim-id>","status":"confirmed","confirmation":"sha256:<fingerprint-of-new-portal-evidence>"}`. On ambiguity, use `"status":"uncertain","confirmation":null`. The receipt labels the evidence as an agent-observed portal confirmation. If the Store revision changed after the click, the receipt survives and the existing job record is left for reconciliation. Stop on any uncertain result for that job and ask the owner to verify it before any manual retry. Keep approval and claim identifiers private. Remove private inputs after the operation.

Turning the switch off blocks subsequent claims. Previously consumed attempts remain available to report their outcomes. Turning it back on requires new approval. The owner can always choose to submit personally from the visible review page.
