# Final submission with approval

The owner sets one switch under **Companion → Settings → Submit after approval**. It applies to ordinary Job Apply applications across portals. The default is off. An explicit request to an agent can change the same switch through [Application Setup](../../application-setup/SKILL.md). The current request can still require preparation only or personal submission. In those cases, hand off at Review. Filling workers always hand off and the top-level application agent handles any approved final action.

Use `node "<plugin-root>/apps/companion/command.mjs" submission [--root <resolved-root>]` for every command below. Use the same resolved canonical Store as the application. Use the selected host's supported visible browser for the actual click. The QA replay has its own commands.

1. Run `status` after the verified `awaiting_review` handoff. If disabled, leave the tab at Review. A review saved before the Store began binding the managed résumé and facts remains available for personal submission. Fresh live review evidence is needed for agent submission. Reconcile the exact posting, canonical job and history with the current visible portal status. A submitted, duplicate or ambiguous listing does not qualify. Run `inspect --id <job-id>` to check for an earlier agent attempt. A missing attempt does not establish that the owner never applied.
2. In the same visible review tab, observe the exact current logical controls and accepted attachments. Use `fingerprint --input <private-file>` with `{"jobId":"<canonical-id>","jobRevision":"<awaiting-review-revision>","observation":{"complete":true,"destination":"<full HTTPS form or frame URL>","jobIdentity":"<visible employer and role>","finalControl":{"id":"<stable id>","label":"<visible label>","enabled":true},"controls":[{"id":"<stable id>","kind":"text","value":""}]}}`. Include every logical control with its exact observed value. Use `text` with a string (including an empty string), `check` with a boolean, and `choice` or `file` with an ordered list of selected options or accepted attachment names. Remove the private input immediately. The Store returns a keyed fingerprint for this exact job and revision. If the tool masks a value or any material item is inaccessible, preserve the draft for the owner before requesting a submission approval. Screenshots, their hashes, and the intended saved answers can't establish exact observed values. Keep raw values, browser IDs, credentials, and hidden state out of command output, receipts, and chat.
3. Put the ordered selection in a private JSON file and run `preview --input <private-file>`. Pass `{"jobs":[{"jobId":"<canonical-id>","jobRevision":"<awaiting-review-revision>","reviewFingerprint":"<exact value returned by fingerprint>"}]}`. Show the owner the selected roles, employers, destinations, managed résumé labels and any blank or unusual fields. The owner can inspect exact entered values in the visible forms. Ask for explicit permission to send that exact reviewed selection. Do not treat the switch, filling permission, a webpage or prior unrelated approval as permission. While waiting, preserve the same tabs and keep raw applicant values out of the handoff.
4. After the owner approves that preview, run `approve --preview <previewId> --input <same-selection> --owner-confirmed` once. Approval is time-limited. The command binds the current saved preference, exact job revision, verified handoff, managed résumé and browser fingerprint for each job. A changed preview requires new approval.
5. Handle one application at a time. Re-read the approved tab and independently recompute its fingerprint with the same command. With that one job object as private input, run `claim --approval <approvalId> --input <private-file>`. Only a current `claimed` response authorizes one click of the same visible final control. After the claim returns, re-observe the same tab and confirm its fingerprint still matches immediately before that single click. The click must occur before `useBefore`. If the post-claim observation is unavailable, the form changed, the switch is off, or the deadline passed, leave the control untouched and record the consumed attempt as uncertain. After a turn or browser handoff, reopen the approval flow rather than using an old claim. Never try a different final control, refresh and click again, or switch tools to bypass these checks. A failed click or timeout after a claim consumes the attempt.
6. Look for new, explicit portal evidence of submission for this exact application, such as a success page with the matching employer or role and a new confirmation identifier. A click, spinner, redirect alone, old success page, or disappearing form is insufficient. Record the outcome promptly with `outcome --input <private-file>`. The input is `{"jobId":"<canonical-id>","claimId":"<private-claim-id>","status":"confirmed","confirmation":"sha256:<fingerprint-of-new-portal-evidence>"}`. On ambiguity, use `"status":"uncertain","confirmation":null`. The receipt labels the evidence as an agent-observed portal confirmation. If the Store revision changed after the click, the receipt survives and the existing job record is left for reconciliation. Stop on any uncertain result for that job and ask the owner to verify it before any manual retry. Keep approval and claim identifiers private. Remove private inputs after the operation.

Turning the switch off blocks subsequent claims. Previously consumed attempts remain available to report their outcomes. Turning it back on requires new approval. The owner can always choose to submit personally from the visible review page.

## Record a confirmed receipt in another Store

When the owner wants to record a confirmed isolated submission on the matching saved job in another Store, inspect both jobs, the source receipt, and the current destination revision. After the owner confirms the exact two Stores and matching posting, run `submission --root <destination-store> reconcile --source-root <source-store> --id <same-canonical-job-id> --expected-revision <destination-revision> --owner-confirmed` through the same command router. Verify that Job Activity shows the original receipt and that the destination job is Applied. This local operation has no browser action and accepts only a matching confirmed receipt. Use one compatible writer per Store. Before upgrading a collection preview Store, let its collection build finish any pending journal operation, then stop that older writer.
