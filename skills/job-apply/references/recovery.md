# Reviewed and blocked jobs

Read only for the exact selected reviewed or blocked job. Use the initialized Store routing from answer-memory and the private attempt helper; never recover raw claims through an ordinary agent.

- If the exact owner-selected job is `awaiting_review`, do not select it as Ready and do not restart merely because the owner said “continue.” Inspect its value-free activity and ask the owner to confirm explicitly that this application was not submitted. Only that current, job-specific confirmation authorizes one `job-apply-attempt.py ... restart-review --id <job-id> --owner <owner-label> --expected-revision <displayed-revision> --owner-confirmed-not-submitted` launcher. Use the exact displayed revision and stop on any conflict, incomplete review evidence, pending work, existing claim, or failed managed-resume preflight. Modern sessions require the complete prior review envelope. A legacy session is eligible only when `attemptRevision`, `readiness`, and `browserHandoff` are all structurally absent, its exact state is `review`/`final_review` with no pending work, its latest same-job history anchor is `reviewed`/`awaiting_review`, and it has no prior restart. Partial, explicit-null, malformed, or contradictory metadata is not legacy and must fail closed. The detached broker then owns the same job exactly as for `start`; prior review-session bytes remain intact until a successful claim-gated `progress` write. Treat missing legacy readiness as unknown: rebuild the visible application from the beginning and produce fresh current-attempt readiness and browser handoff before review. This restart does not authorize opening a browser, entering data, or activating a final action; apply the ordinary visible-browser and action-time-consent rules again.

- If the exact job is `needs_info` with a pending answer reference, first inspect `job-apply-task.py ... activity --id <job-id>`. Route the owner to the canonical Answers editor; do not infer, reveal, or copy an answer value. After the owner has explicitly saved an accepted, confirmed, non-sensitive answer, run `job-apply-task.py ... resolve-pending-answer --id <job-id> --reference <pending-reference> --expected-job-revision <activity-job-revision> --expected-session-revision <activity-session-revision> --expected-answer-revision <pending-answer-revision> --owner-confirmed`. Never use this operation for missing, inferred, declined, sensitive, unreferenced, or changed answers. Never retry a stale failure: refresh activity, preserve any browser draft, and ask the owner to review the changed canonical state. The result remains `needs_info` while any blocker remains; when it returns the exact job as Ready, pass that returned revision unchanged to a new private attempt helper process. The same job/session and assigned-or-default managed resume identity continue across blocking, resolution, the new private attempt, and awaiting-review handoff; do not substitute a resume or source path. This recheck does not open a portal or authorize any final action.
